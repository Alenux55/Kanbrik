# Architecture constraints and candidate model

The implemented sections record tasks 001–009; capture sections remain a planning contract. The selected stack is in stack.md. The target is an always-online Ubuntu server; Docker availability on that server has not been verified by the implementation agent.

## Implemented foundation, identity, and sharing (tasks 001–003)

- One Next.js App Router application with TypeScript and React. A protected route-group layout owns navigation; a section route renders five clearly labeled placeholders. `/` redirects to `/projects`; unknown sections return 404 for authenticated users. Server page and layout checks verify the database-backed session, not merely cookie presence.
- The shell uses Tailwind CSS and a repository-owned, simplified shadcn/ui badge and utility convention. Navigation is ordinary links, supports keyboard use, and reflows into a grid on narrow screens without a drag dependency. Fonts are local system fonts.
- Better Auth email/password identity and database-backed sessions are implemented for local/test use. `/sign-in` and `/sign-up` are public; `/api/auth/[...all]` mounts the library handler. Library origin/password/session protections remain enabled; cookie session caching is disabled so revocation/expiry is checked against PostgreSQL. Secrets/database access stay in server-only modules. Generic errors avoid exposing database details. Sign-in/out force a full document navigation to discard prior client router state.
- The original local/test signup policy requires its explicit flag and a loopback trusted app URL. Task 010 adds a separate explicitly enabled HTTPS preview profile below. No `NODE_ENV` registration fallback exists; default production mode still denies signup. General public-registration/invitation policy remains open.
- The first authenticated planner request invokes transactional personal-workspace bootstrap. The signed-in state and actual personal-space name are displayed. Workspaces management implements shared creation and owner/editor access. Projects/tasks and Board's saved selection were added in tasks 005/008 below. Global active-workspace selection remains unimplemented; Calendar has separate view preferences below; no ownership transfer, role-change or workspace-kind-change endpoints exist.
- Prisma 7 client with its PostgreSQL driver adapter and a checked-in migration implement the four Better Auth tables plus `Workspace` and `Membership`. `personalOwnerId` is unique, workspace/user membership pairs are unique, and SQL constraints require personal kind/owner consistency. A migration trigger allows only the personal owner's `owner` membership. Task 003 reuses the shared kind/editor values without a new migration or changes to the applied migration.
- `personalWorkspace(headers)` derives identity from a verified session, takes a per-user PostgreSQL transaction advisory lock, upserts workspace and owner membership, and commits them together. Unique constraints enforce identity even under concurrency; repeated requests return the same ID. Missing workspace or membership after interrupted onboarding is repaired from verified owner identity. No client user/owner ID is accepted.
- `POST /api/workspaces/personal` requires an authenticated session, exact trusted Origin, and strictly empty JSON object. Personal access always requires both owner identity and owner membership; shared access requires a current membership. The shared branch never drops the personal-owner predicate from personal reads. API responses use `no-store`; protected pages are dynamically rendered and uncached. No user-dependent result enters a shared application cache.
- Local Compose reserves a loopback-only PostgreSQL 17 development database and an optional app profile with registration disabled. The multi-stage Dockerfile uses Next.js standalone output and a non-root runtime. Docker/image availability and container execution remain unverified locally; this is not production configuration. A portable PostgreSQL 17.11 process, separate roles/databases, migrations, and integration tests have instead been verified on Windows.
- Browser checks target a production-mode local build, with authentication enabled and a dedicated test database. Unit guards reject unsafe test database targets; integration tests exercise the real HTTP auth boundary, database constraints, transaction rollback/recovery, concurrency, isolation, and revocation. Tests create unique users and delete only their own fixtures. Real Android/Linux/container behavior remains unverified.

### Shared-workspace contract (task 003)

- `GET /api/workspaces` lists only the caller's accessible personal/shared workspaces as `{id, name, kind, role}`. It also recovers initial personal onboarding. `POST` accepts strictly `{name}` (trimmed, 1–100 characters), creates shared kind with no personal owner ID, and creates the verified actor's sole owner membership atomically through a nested write.
- `GET /api/workspaces/[id]` returns the same safe summary plus minimal members `{id, name, email, role, isYou}`. It never returns whole user/session/account records. Anonymous API requests receive 401; inaccessible IDs receive 404 with no name/roster/owner details. An insufficient role in an accessible workspace receives 403.
- `POST /api/workspaces/[id]/members` accepts strictly `{email}`; trim/lowercase follows Better Auth's stored email convention. Only an owner can grant editor access to an existing account. Repeated/concurrent grants preserve one membership. Adding the owner as editor is rejected without modifying its role. This immediately grants access; it is not invitation delivery or identity verification.
- `DELETE /api/workspaces/[id]/members/[membershipId]` requires an owner and a target editor membership scoped to that same workspace. `POST /api/workspaces/[id]/leave` permits only the verified editor's own membership to be removed. Both accept strictly empty JSON bodies. Personal targets, owner changes, forged actor/role fields, and cross-workspace membership IDs are rejected. There are no endpoints for multiple owners, owner leave/removal, demotion, conversion, or deletion.
- Membership mutations check access, lock the workspace row for the transaction, and then recheck the caller's current membership/role before writing. The same lock serializes editor grants/removals/leave, while database uniqueness enforces pair identity. Revocation denies later reads/writes in that workspace without invalidating the account session or its personal/other-workspace access. Already downloaded information cannot be retracted.
- All new writes require verified sessions, validated input, and exact trusted Origin. `workspaceRequest` returns deliberate status/safe error shapes; unknown server/database errors are generic. The client shows pending/confirmed/failed states, retains unsaved form input after failure, and refetches access after successful changes. A missing membership on refresh/action clears the working roster; stale UI grants no server authority.
- `/workspaces` and `/workspaces/[id]` are protected management pages, reachable from navigation. They show kind/role and an explicit management target. The sidebar names only the personal space, not a global active selection. Content views remain placeholders.
- The root error boundary uses Next.js 16.4.5's stable `retry()` prop (available since 16.3), verified in its bundled docs, types, and implementation: refresh then reset. It retries only on user action, with a pending button and another retry if failure continues. Browser regressions inject a membership-write failure scoped to one disposable fixture inside guarded PostgreSQL, without an application failure endpoint or authentication bypass.
- Single owner plus editors, and immediate exact-email grants, are bounded development defaults used by this task. Public signup/invitation policy, verified identities, and ownership administration remain open product decisions.

### Password confirmation and recovery (task 004)

- `npm run email:check` loads Next's development environment-file precedence and calls the same pure configuration validator as the server. It reports invalid setting names and inherited-shell overrides without values, raw validation errors, or network connections. SMTP connectivity/delivery is a separate check; public recovery pages still expose only the generic configured/unconfigured state.

- `SMTP_FROM` accepts a plain email address or `Display Name <email>` (including a quoted display name). It is validated as one mailbox and passed to Nodemailer as a structured name/address object for safe header formatting. Invalid addresses, multiple mailboxes and embedded control characters are rejected.

- Explicitly requested follow-up to the identity slice: sign-up confirms the password locally before making an auth request; the extra confirmation is not a new stored credential or API authentication mechanism. Sign-in links to public `/forgot-password`; `/reset-password` accepts an emailed token and confirms the new password. Pending/error states retain recoverable input, and successful reset requires a fresh sign-in.
- Better Auth 1.7.18 owns reset token generation, one-hour expiry, atomic single use, password hashing, and session revocation. Its Prisma adapter now enables transactions explicitly so token consumption, credential update and database session revocation commit together. Reset preserves canonical users, workspaces and memberships. The existing Verification table supports this without a migration.
- Nodemailer sends plain-text recovery links via server-only SMTP configuration. Email requests are disabled until `PASSWORD_RESET_ENABLED=true` and required host/port/user/password/sender fields validate. Normal SMTP requires STARTTLS or implicit TLS with certificate validation; a plaintext exception is restricted to explicitly enabled loopback local/test mail capture. No mail credentials or URLs/tokens are logged, returned as diagnostic API data, or added to client bundles.
- The application fixes reset destinations to its configured trusted app URL, and requires the exact trusted Origin for reset POSTs, in addition to the library's checks. Known/unknown addresses receive the same generic normal request response; unexpected delivery/database errors remain generic and retryable. SMTP acceptance is not proof of inbox placement. Account email verification/public-signup policy remains separate and deferred.
- Email links place the library-generated token in the reset page's URL fragment, not a server-visible URL path/query. The client reads it after hydration, removes the fragment from history, and submits it only in the reset POST body. Reset pages set no-referrer policy; there is no browser storage queue or token persistence. Users can reopen the email link after an interrupted reload.
- Automated checks use actual PostgreSQL, real HTTP boundaries, and a test-only loopback SMTP sink. Inbox contents stay in memory behind a per-run test secret; there is no application mail-inspection/failure endpoint. Fixtures contain generated accounts only. Real provider delivery, spam filtering and production email/TLS setup remain unverified until configured by the owner.

## Projects and tasks (implemented task 005)

- `Project` and `Task` are canonical workspace-owned records added by `202611050002_projects_tasks`; the original applied migration is unchanged. Both have stable IDs, title, plain-text description, timestamps, and revision starting at 1. Task adds fixed status (default `todo`), optional project, and optional parent task. The shared status labels/completion definition live in `src/lib/task-statuses.ts`; PostgreSQL's enum rejects unsupported IDs.
- Composite foreign keys `(projectId, workspaceId)` and `(parentId, workspaceId)` prevent foreign-workspace references. A trigger enforces NULL-safe parent/project equality and a root-only parent; a child is the same Task model and cannot have children. Self-parenting, invalid lengths/revisions, and context changes are rejected in SQL too. Task workspace/project/parent and Project workspace assignments are immutable in this slice. Server validation gives deliberate errors before writing. Parent/child statuses never cascade.
- Workspace owner/editor access follows the existing personal-owner predicate and shared membership boundary. `workspaceContent` verifies the session, checks scope, takes the same workspace row lock used by membership mutation, then rechecks current access inside the transaction. Content operations (including reads) serialize with membership removal. A queued removed editor cannot write after the removal commits; content authorship adds no private sharing exception.
- `src/server/planning.ts` centralizes list/detail/create/update operations. Resource collections are `/api/workspaces/[id]/projects` and `/api/workspaces/[id]/tasks`; details append `/[recordId]`. GET collection returns an array ordered by creation time then ID; GET detail returns one record. POST returns 201 and the committed record. PATCH returns 200 and the committed record. Responses contain scalar record fields only (timestamps serialize as ISO strings); no user/session/membership records. Reads/responses use `no-store` and protected pages are dynamic.
- Project POST accepts strictly `{title, description?}`; Task POST accepts strictly `{title, description?, status?, projectId?, parentId?}`. The path supplies the authorized workspace; a subtask derives project/workspace from its authorized parent, with contradictory project input rejected. Project PATCH requires `{title, description, revision}`; Task PATCH adds required `status`. Revision is a positive integer expected by the caller. Unknown keys, actor/ownership fields, status values, and immutable assignment edits fail. Mutation requests require the exact trusted Origin. No DELETE/archive/move operation exists.
- Updates compare the supplied revision and increment it atomically. HTTP 409 includes `{error, current}` only after authorization. Same-revision competing writes yield one success and one conflict. HTTP 401 means sign-in required, 404 hides inaccessible/missing workspace or record IDs, 400 covers invalid fields/relationships, 403 rejects untrusted mutation Origin, and 503 is a generic unconfirmed failure. SQL failure rolls back text/revision together.
- `/projects` replaces its placeholder with explicit workspace selection, project list/detail forms, standalone/project tasks, and subtasks. Shared changes arrive on selection/navigation, the caller's completed save, or **Refresh planning**, without live push or polling. Requests ignore superseded load results. Each save confirms only a committed server response; loading other people's edits never replaces a dirty draft.
- `PlanningDrafts` retains only in-memory drafts keyed by workspace/entity/record or create context. It spans planner navigation; saved revisions stay with edited drafts. A session-level in-flight lock survives form unmount/navigation, and successful saves refresh current views. There is no browser storage queue. Reload/close warns about dirty drafts when supported; sign-out clears drafts and allows exit. Task 006 replaces reliance on the server-layout user key alone with the verified session boundary below; the independently reproduced gap at `0929f9a` is retained in task 005's review history.
- Conflicts keep editable draft text, show the saved text/status/revision, and disable save until **Load saved version** or **Review complete: keep my draft**. Keeping a draft adopts the reviewed revision for a later explicit save; it does not automatically overwrite. A later competing edit can cause another conflict. Failed saves retain unsaved input, and 401/404 on content fetch/action removes the working protected view and that workspace's drafts. Previously downloaded data cannot be retracted.
- Database delete cascades serve existing account/workspace lifecycle and scoped test cleanup, not new content deletion endpoints. A future lifecycle task must define user-visible delete/archive/restore behavior before exposing it. Board/Calendar/Lists/Inbox remain placeholders and do not claim to display the new records. Existing auth/recovery/membership/retry behavior remains in place.

## Verified planner session boundary (task 006)

**Historical finding at `0c13917`, corrected in task 007:** the old library verification response could renew/delete cookies and restore A after B signed in. Epoch checks cannot control browser cookie headers. The replacement `GET /api/planner-session` creates its own no-store JSON response containing only `{userId: string | null}` (or a generic 503 error). It never forwards library response headers, including on invalid/expired/error paths. Task 008 still waits for independent review of this correction.

- The protected layout wraps the entire shell in `PlannerSessionBoundary`. Its coordinator now reads `/api/planner-session` with no-store and the existing timeout/version/epoch behavior; the public `verify`/protected-fetch abstraction is unchanged for future Board integration. The server probe uses verified database-backed Better Auth sessions with both `disableCookieCache` and `disableRefresh` true. All shared `verifiedSession` calls use those flags, preventing planner actions from silently extending a valid session's lifetime. The library may clean up an already-expired database session; none of its cookie deletion headers can reach the browser through this probe.
- Renewal is separate from identity probing: a deliberate successful sign-in establishes a fresh library-managed session. The normal Better Auth endpoint retains its renewal/cookie behavior for deliberate auth consumers, and sign-in/out/reset security is unchanged. The planner never uses that cookie-mutating endpoint for identity checks. A delayed null probe may conservatively gate the old tab at sign-in even if another tab has since signed in; it cannot erase that newer account's cookie. No global cookie-security or authentication policy flag was weakened.
- Checks run on initial mount, planner pathname changes, focus/visible resume, `pageshow`, authentication storage pulses, and protected actions. There is no polling loop. Successful signup/sign-in/sign-out/reset publishes only a fresh non-secret invalidation nonce; no identity, token, credential or draft content is stored/broadcast. Better Auth's storage signal is also a hint. Installed 1.7.18 source showed its session-atom refresh manager is activated on subscription and sign-in is not the same as a guaranteed cross-tab broadcast; the application does not assume an unused client hook will synchronize the shell.
- Signals invalidate pending checks using a version counter. Outdated verifier responses cannot make a new context ready. User IDs are compared, not session-object references, renewal timestamps or expiry metadata. Checks deduplicate current concurrent verification; a later auth signal requires a new check. Failures/timeouts show a neutral retry view, retain the original account's in-memory state, and do not infer logout. Hidden/inert protected children stay mounted during a same-user check so drafts, selection and conflict state survive.
- On a verified identity change or logout, the coordinator advances its context epoch, aborts outstanding protected fetches, clears drafts/selection/pending-save bookkeeping, suppresses the obsolete draft-unload prompt, and replaces the document with `/projects` or `/sign-in`. This refreshes header, authorized workspace options and content together and prevents router-cache resurrection. Unmounted coordinators stop affecting the document; immediate Strict Mode effect reattachment is distinguished from actual unmount. A previously authorized server transaction can still commit; aborting its UI response never promises rollback.
- Protected planning/workspace requests verify before dispatch and after consuming the network response, carry their original user/epoch, and reject obsolete completions. Draft setters/save-lock completion and local callback guards also check that context. Account B receives a fresh provider/document; an account-A completion cannot navigate it, populate its forms, clear its draft, release its pending-save lock or claim success for it. Same-account revision conflicts and membership revocation retain their original server contracts.
- Protected UI requests send `X-Kanbrik-Account` as an expected-account precondition. `verifiedSession` rejects a mismatching header with `SessionChanged`; workspace APIs and sign-out return safe HTTP 412 / `SESSION_CHANGED`. This closes a cookie change between client verification and dispatch. The header is optional for existing API consumers and **never selects or authorizes an actor**: server cookies/session and membership remain authoritative, and a matching/omitted header cannot grant access. Sign-in is an intentional public account change. Verified same-tab sign-out carries the expectation too.
- Synchronization is event/action based. A suspended tab cannot erase information already viewed/downloaded; it rechecks when it resumes or acts. Browser storage may be unavailable, so focus/navigation/actions remain independent verification paths. Drafts are not durable/offline state, and network failure pauses editing until identity can be verified again.

## Kanban implementation (task 008)

- Owner confirmed task 007 was approved before this implementation began. Its committed baseline is `47993fa`; no auth-probe implementation was bundled into the board diff. Board uses `PlannerSession.fetch` and account/epoch context checks, not a separate verification endpoint or actor selection mechanism.
- `BoardPreference` is a user-owned row (`userId` primary/foreign key with user-delete cascade) storing `workspaceIds: String[]`, added by `202611060001_board_preference`. Existing data/migrations are unchanged. No BoardTask/Card table exists. GET `/api/board/preferences` returns accessible workspace summaries plus selected IDs: missing row defaults only to personal, saved empty array stays empty, inaccessible saved IDs are filtered from the response. The stored array is not authorization. Rejoining a workspace can make its previously saved ID eligible again; no preference cleanup GET overwrites a concurrent explicit selection.
- PUT accepts strictly `{workspaceIds:string[]}`, validates each against current accessible workspaces, deduplicates and upserts by the verified session user. No owner field is accepted. Same-user preference writes use last-committed selection, independently of task revisions. Responses are no-store; anonymous callers get 401, foreign/inaccessible IDs safe 404, forged/unsupported fields 400, wrong Origin 403 and mismatching account expectation 412. Membership can change after a preference check; every subsequent content read/write still reauthorizes independently.
- Board loads task/project lists through existing workspace-authorized operations, with no card cap or whole-account aggregation cache. Each selected scope is loaded independently. Failure removes that scope's editable cards and labels counts incomplete; successful scopes remain available with the warning. A 404 clears the affected working scope/options/selection. Loads are bound to selection mount/version and identity, so old results cannot reinsert deselected cards. Refresh hides old selection controls until preferences finish loading, preventing late preference reads from overwriting new checkbox input.
- PATCH `/api/workspaces/[id]/tasks/[recordId]/status` accepts strictly `{status,revision}` using the central five IDs. It reuses `workspaceContent`'s session, workspace lock/recheck, privacy and safe-conflict handling. An atomic revision compare/increment updates only status and normal timestamp/revision; title/description/project/parent/workspace are preserved. A queued removed editor is denied after the lock, and same-revision text/status edits have one winner plus 409 with safe current state.
- UI updates are confirmed after server commit, without optimistic movement. Shared in-memory save locks (`board:<taskId>`) span board selection/navigation and are scoped by the existing verified provider. An unmounted selection ignores completion data; the same user's committed completion releases only its own lock and signals current views to refetch. New-account callbacks cannot alter preferences/cards/locks. Projects drafts retain their original revision and must resolve normal conflicts after a board change.
- Five desktop columns use stable creation-time/ID ordering. Standalone/project tasks and subtasks are individual canonical cards with independent completion, authorized context and native accessible details. `@dnd-kit/core` mouse dragging is handle-only with an eight-pixel activation distance. Same-column/canceled drops do not write. Selection changes unmount/cancel the drag. Keyboard/touch moves use labeled native status selectors with accessible saved/error messages and focus on the moved card's selector. Android uses selectable status tabs/counts, not precision dragging.
- No global active-workspace preference, calendar selection, manual ordering, custom workflow, moves/reparenting, deletion/archive or offline queue is implied. Live updates require Refresh board or own successful save. Lists/Inbox remain placeholders; Calendar follows below.

## Calendar implementation (task 009)

Task [009](tasks/009-calendar-time-blocks.md) builds on reviewed application baseline `500b136`. These are bounded implementation defaults, not additional user-confirmed requirements.

### Storage and authorization

- Additive `202611060002_calendar` creates `TimeBlock`, `CalendarPreference` and `CalendarCreateIntent`; prior migrations and canonical work are unchanged. Block start/end are PostgreSQL `timestamptz(3)` instants, serialized as UTC ISO strings. The separate IANA editing zone retains context. Label is server-trimmed 1–200 characters (database default `Time block`); revision starts at 1, with ordinary timestamps.
- SQL checks enforce positive revision, end after start, nonblank/bounded trimmed label and at most one assignment. Composite project/task foreign keys enforce the block's workspace. A trigger rejects workspace changes and unknown PostgreSQL zone names. Project/task deletion is restrictive rather than cascading through blocks. Workspace deletion remains a cascade; owned test cleanup explicitly removes blocks first to satisfy restrictive linked-work relationships. There is no work/workspace deletion UI.
- All content operations use verified sessions and `workspaceContent`'s existing workspace lock/recheck. Personal owners and shared owners/editors have the same content rights as tasks. Linked records are validated inside that transaction. A matching account header, display selection or known block ID never grants access. Reads expose minimal current project/task assignment context, not copied work data or session/user objects.
- Creates/edits/removals never update canonical work fields, status, completion or revisions. Block removal removes only that block. Shared blocks are a shared workspace plan, not personal availability reservations. Private scheduling of shared work across workspace boundaries remains deferred.

### HTTP contracts

All responses are no-store. Existing safe 400/401/403/404/409/412/503 handling, exact trusted Origin for writes, verified-account preconditions and sanitized failures apply.

| Operation | Strict input and result |
| --- | --- |
| GET `/api/workspaces/[id]/time-blocks?start=…&end=…` | Offset-bearing start/end, positive interval at most 93 elapsed days. Returns every overlapping authorized block, ordered by start/ID, without an event cap. |
| POST collection | `{requestKey,label,schedule:{startAt,endAt,timeZone},assignment:{projectId,taskId}}`. UUID request key, nullable references with at most one non-null. Returns saved block with current assignment context (201). |
| PATCH `…/time-blocks/[recordId]` | `{revision,changes:{label?,schedule?,assignment?}}`; at least one group. Schedule always includes both boundaries and zone; assignment includes both nullable IDs. Unsupported fields are rejected. Returns the new block/revision. |
| DELETE record | `{revision}`; returns `{deleted:true,id}`. Missing/deleted records get safe 404, stale revision gets 409 with current authorized state. |
| GET `/api/calendar/preferences` | Accessible workspace summaries, selected IDs and saved zone (null before first save). Missing row defaults only to personal; saved empty remains empty. Inaccessible IDs are filtered without writing over preferences. |
| PUT preferences | `{workspaceIds,timeZone}`; verified actor owns the row. Validate/deduplicate accessible IDs and IANA zone, reject forged owners. Return saved IDs/zone. Independent of Board/Projects; same-user preference writes use last-committed semantics. |

Block edits and deletion compare expected revision under the workspace lock. All edit groups share one revision, so concurrent label/schedule/assignment writes have one winner; no automatic refetch-and-retry overwrites another edit. The create-intent ledger has workspace/request-key identity and retains the parsed payload plus block ID. Identical retries return the original current block; changed payload with that key gets 400. Intent rows deliberately survive block deletion: retry then gets 404 and cannot recreate it. There is no retention/expiration job in this slice.

### Time semantics

- Zone conversion uses Luxon/Intl rather than server-local Date parsing. Local input is round-tripped to reject spring gaps; `getPossibleOffsets()` supplies both repeated fall occurrences with numeric offsets. A repeated boundary requires an explicit form choice. Schedule input must carry offsets matching the named zone at each instant. Start and end may legitimately differ across DST; an offset cannot bypass the zone rule.
- Intervals are half-open: `block.startAt < rangeEnd && block.endAt > rangeStart`. Spanning/multi-day blocks are included; adjacent boundaries are excluded. Day/week boundaries are calculated in the display zone using calendar arithmetic, not a fixed 24-hour approximation. Weeks start Monday in both query and grid.
- Overlaps are allowed. Pointer moves preserve elapsed duration; resize changes its selected boundary. Pointer snapping is 15 minutes; explicit minute values are not rounded. Forms preserve unchanged second/millisecond instants and submit only intentionally changed groups. Actual elapsed hours are shown. Ambiguous pointer boundaries require explicit occurrence confirmation before saving.
- Time-zone rules come from the Node/browser Intl databases (database trigger checks zone-name existence). Keep these runtimes current: political time-zone changes can otherwise disagree. Tests use a currently DST-observing zone, `America/Los_Angeles`; current IANA data makes Vancouver permanent UTC−07 after March 2026, so it is not a valid 2026 fall-fold fixture ([IANA 2026b](https://www.iana.org/time-zones/releases/2026b)). Stored instants do not depend on host time zone.

### Client lifecycle and interactions

Desktop FullCalendar Standard provides week/day grids, move/resize and previous/next/Today controls. Android defaults to a day agenda; all create/assign/replace/unassign/edit/remove operations use labeled forms and buttons. The Calendar-local dnd-kit MouseSensor palette assigns work only onto existing empty blocks in the same workspace; it does not use FullCalendar's external event-creation feature. Assignment keeps the ID/interval/count and source work. Occupied/foreign targets explain the explicit alternative and make no write. No-op/Escape/context-change gestures do not write. The grid and agenda have distinct target IDs referring to the same canonical block.

Calendar drafts extend the existing account-scoped in-memory provider with original revision/base, editing zone, input and stable create key. Ordinary navigation, date/zone changes, current-data refresh and background saves do not rebase dirty input. Unload warns when supported. Failed gestures become retained form drafts. Conflicts show saved state beside proposed input, require review and then a later explicit save. Explicit edits send changed groups only. An uncertain create freezes its payload for original-intent retry; discarding it explicitly starts another key and does not promise an earlier request rolled back. An uncertain delete retains confirmation and revision; retry checks record absence separately from current workspace access. The retained-draft list lets users review original records outside the loaded range or reconcile removed blocks after navigation, without counting those drafts as saved events.

Shared `calendar:<blockId>`/new-intent locks prevent duplicate actions across navigation/selection. Mutation callbacks retain account/epoch and mounted range/selection context; obsolete results cannot repopulate another view or clear another account's draft/lock. A same-account committed save can signal current views to fetch. A record mutation's 404 is followed by a separate authorized workspace read: confirmed workspace 404 clears that workspace's blocks, work options, details and drafts. With access still confirmed, a missing gesture target is removed from saved events while its proposed input, workspace selection and unrelated drafts remain. A failed access recheck stays unconfirmed and preserves input. Recheck completions from an unmounted range/selection or obsolete account cannot revoke the current view. Failed scopes lose editable stale events and mark counts incomplete; work-picker failures are separately labeled and disable affected assignment/create forms. Manual refresh reloads preferences with controls hidden until completion, preserves dirty block forms and refuses to discard unapplied preference input. Live push, browser persistence and offline editing remain deferred.

## Planned usability/settings contracts (task 011)

The [011 feedback and staged design](tasks/011-planner-usability.md) is a proposal, not the current runtime contract. Keep the implemented sections above as historical/current evidence until the respective slice is implemented.

- Separate an account-owned default creation workspace from per-view visibility filters and from each record's immutable workspace ownership. Contextual parent/project/work references constrain creation; existing editors must not silently substitute the global default.
- Reuse canonical entity editors and their original revision/intent/account-scoped draft state across views. Responsive modal presentation changes layout, not server authorization, save/conflict semantics or deletion/revocation distinctions.
- User settings will own the saved zone for display and ordinary time entry, migrating the existing Calendar preference without losing its value. The owner clarified that each workspace has a canonical IANA zone representing its shared location; users create/edit/view from their own zone, independently of server location. Persist authoritative UTC instants and the workspace zone separately and derive both local representations. Do not store an ambiguous workspace-local timestamp alone. Changing preferences/zone metadata does not move instants; dirty forms retain their captured input zone. ## Candidate entities

| Entity | Responsibility |
| --- | --- |
| User | Identity and display time-zone preference |
| Workspace | Personal/shared ownership boundary with a name and visual identity |
| Workspace membership | User/workspace relationship and owner/editor role |
| User view preference | Selected workspace IDs; never grants membership |
| Project | Workspace-owned planning context and description |
| Task | Canonical work with workspace, optional project/parent task, and status |
| Status definition | Central fixed definitions with stable IDs; no customization initially |
| List/checklist | Workspace-owned simpler task/item organization; exact item semantics remain open |
| Time block | Workspace-owned start/end/time-zone context and optional project/task reference |
| Inbox item/note | Workspace-owned capture or reference content |

Personal work uses a one-member private workspace, not a separate task model. There are no project-specific sharing overrides initially. Initial personal-workspace creation must be idempotent.

## Ownership and authorization

- Every domain record has a workspace ID. Check membership on the server for all reads/writes, lists/searches, nested content, relationship changes, and membership management.
- Relations/constraints reject inconsistent ownership: tasks and their projects/parents share a workspace; assigned blocks reference work in their own workspace.
- Requested workspace filters are intersected with authorized scope or rejected if invalid. Client selection alone never grants access.
- Define role capabilities centrally. Proposed owners manage membership/settings; editors manage work. Prevent removal/demotion of the last owner. Personal workspaces cannot implicitly acquire collaborators.
- Use an established authentication/session solution. Identifying a user does not replace workspace authorization.
- Private scheduling of shared work must not duplicate tasks or relax ownership constraints. Design an explicit cross-workspace visibility/reference contract if required.

## Board and status invariants

- Centralize backlog, todo, in_progress, blocked, and done as stable IDs, with labels and completion meaning defined once. Only done means complete.
- All workspaces use the same five statuses initially. The combined board groups directly by status without workflow mapping.
- Card moves change status and preserve workspace/project identity. Reordering never silently transfers ownership.
- Project, board, list, and calendar share canonical tasks and application operations.
- Central definitions reduce future customization cost. Workspace-specific statuses would still require deliberate schema/API evolution and data migration; do not build the editing system now.

## Scheduling and integrity

- Initially propose empty blocks or one assignment to existing work in the same workspace. Multiple blocks may reference the same work.
- Moving/resizing changes the schedule, not task status or due date. Removing blocks never deletes work.
- Require end after start. Document the storage/time-zone convention before implementing scheduling, including daylight-saving transitions.
- Prevent parent-task cycles and define parent completion rules before implementing nesting.
- Define archive/deletion behavior before destructive actions; do not silently remove related work.
- Workspace selection is a per-user display preference. Clearing it yields an explicit empty state; creation needs an unambiguous destination workspace.

## Persistence and concurrent updates

- Use persistent server-backed storage shared by authorized users/devices.
- Document fetch/refresh behavior. Live push updates are optional initially.
- Use explicit revision checks or another documented concurrency mechanism for user-edited shared content. Avoid silent last-writer-wins overwrites.
- Confirm saves only after server success. Preserve recoverable input in the current session after failed saves and allow retry; this is not durable offline editing.
- Separate development/test databases from production. Before real production use, document migrations, persistent volumes, backups, and verify a restore.

## SilverBullet boundary

In the proposed standalone design, Kanbrik owns workspace permissions, tasks, status, and schedules. SilverBullet may hold linked reference notes. Two-way synchronization and embedded planner UI are outside the initial proposal.
