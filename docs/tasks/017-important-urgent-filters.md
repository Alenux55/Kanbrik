## Outcome and inputs

Tasks/subtasks can have multiple user-named tags with autocomplete and a chosen color from the existing project palette. Important and Urgent are ordinary possible names, not special flags. Preserve tag filtering across Projects, Board and Calendar; Calendar additionally filters work by project and general text search. Read AGENTS.md, README, product/architecture/stack, the handoff and final reviewed task 013–016 contracts, especially drafts, Trash/Restore, activity, statuses and filter behavior.

## Confirmed scope and recommended defaults

Confirmed: users can type their own tags; matching existing tags appear while typing; each tag has a chosen color from the project color list. This replaces the earlier fixed Important/Urgent request while preserving filters in the three views. Calendar must offer project, tag and general-text filters.

Recommended defaults: workspace-owned tags and task associations under existing content rights, no automatic parent/project inheritance, and no tags assigned to existing/new tasks by default. Projects are containers/context rather than newly tagged records; subtasks use Task. Multiple selected tags offer explicit Any selected (OR) / All selected (AND); no tag selection means no tag restriction. Project/tag/text categories combine with AND. Filters are independent account-scoped in-memory preferences per view initially. These are recommendations beyond the confirmed features.

## Tag entry, colors and data

- Use an accessible tag combobox in the canonical task/subtask editor. As the user types, suggest existing tags from the current work's authorized workspace, with name/color and keyboard/touch selection. An explicit Create tag action handles an unmatched name; keystrokes alone must not create definitions or assign tags. Prevent stale-query responses replacing a newer query/target/account's suggestions.
- Tags have stable IDs, bounded display names, normalized workspace-unique names and a stored palette color key. Define consistent trimming/case-insensitive matching so Important and ` important ` cannot create duplicates in one workspace. Concurrent creation of the same normalized name reconciles to one tag. Another workspace may use the same name; suggestions/filters must distinguish identities rather than leak or merge foreign definitions.
- Use the existing six project palette colors from `src/lib/board-filters.ts` through one shared palette definition. The current projects use automatic ID-based colors; do not claim they already have a user picker or silently change their existing mapping. Tags have a deliberate color choice, with a sensible default, named swatches, selected-state text and readable contrast. Do not accept arbitrary CSS/HTML as color input or rely on color alone to identify a tag.
- Allow multiple tags per task and removing a tag association without deleting the tag or task. Recommended metadata management includes rename/recolor/archive with its own expected revision; archiving preserves existing associations/history but prevents new assignment. Preserve old labels/IDs in activity and Trash. Recoloring/renaming is not a fake content edit on every tagged task; no permanent purge is assigned.
- Store definitions and associations server-side with same-workspace constraints. Actual assignment/removal uses a clear task/tag-set revision and transactionally records before/after IDs/names under task 014's final event contract. Use stable create intents or equivalent reconciliation to avoid duplicate tags/associations/events on lost-response retry. If an earlier boolean implementation exists in a dependency branch, explicitly migrate it to tags; never keep two competing models or lose values.

## Filters and Calendar search

- Projects retains necessary project/parent context for matching children while distinguishing context from actual matches. A tagged child remains discoverable under an untagged parent; no automatic inheritance or project rollup is implied. Keep counts/empty/incomplete states accurate.
- Board tag filters compose with workspace/project/title/date/status/completion filters and task 016 workflows if implemented. Preserve compact cards, readable colored badges, contained scrolling and same-workspace status moves. Display matching same-named tags with workspace context on multi-workspace views.
- For multi-workspace tag selection, recommend evaluating Any/All against selected tags in the task's own workspace, excluding workspaces with no selected tags while a tag filter is active. Label that rule clearly; selecting Urgent in two workspaces must not require one task to hold both foreign IDs. Do not silently merge definitions by display name. The same rule applies across all three views.
- Calendar offers a compact Filter/search area with project selection, multi-tag selection and text input, plus clear/reset and matching/total counts. Apply a consistent predicate to the task palette, scheduled blocks and agenda; unscheduled matching tasks remain available to schedule. New/edit block pickers may expose all authorized active work when clearly labeled; acknowledge saves hidden by the current display filter.
- Recommended Calendar project semantics: a task matches its own project; a project-assigned block matches that project; standalone work is an explicit choice where needed. Tag filters match the assigned task/subtask's own tag associations, including every block referencing it. Project-only/empty blocks have no task tags and are excluded while a tag filter is active; explain this scope and provide Clear filters. Never infer tags from a project's children or duplicate them on time blocks.
- Recommended text scope is case-insensitive matching of work title/description and displayed project/parent names; scheduled blocks can additionally match their own label. An empty block can match its label only when no project/tag restriction excludes it. Project-only blocks can match their project/label when no tag restriction is active. Clearly describe the search scope; do not silently search private comments/history or introduce full-text infrastructure for this bounded feature.
- Filtering is display-only. Preserve tasks, blocks, intervals, references, statuses, intents and drafts. An already-open/retained draft stays reviewable after its saved item is hidden. Hidden blocks must not become accidental assignment/edit targets; creating a new block on visible blank time retains the existing overlap policy and is not permission to alter a hidden reservation. Coordinate targeting/preview with task 019's final contract.

## Permissions, lifecycle and failure handling

- Every suggestion, definition, association and filter read/write requires current workspace access. Reuse verified identity, expected-account rejection, exact mutation Origin, strict inputs, no-store replies and workspace lock/recheck. Forged task/tag/workspace IDs never grant access. Renaming/recoloring/archiving requires the chosen content/configuration permission on the server, not just hidden controls.
- Tags are independent of status/completion, priority scoring, due dates, checklist/purchase state and scheduling. Work Trash/Restore preserves associations and readable archived definitions without changing existing member revision checks. Task 018 remains sibling-only ordering; tag filters must not let its client mistake a subset for a complete ordering scope.
- Preserve work/comment/list/tag drafts during failed loads and metadata refresh, including rename/archive conflicts and an unsaved tag being edited. Uncertain saves stay visibly unconfirmed. Late query/filter/account responses cannot clear new input or restore inaccessible content. A hidden/nonmatching record is not workspace revocation; genuine membership loss still removes protected data.
